# ADR 0016: Login by phone code

Status: proposed. Items marked CONFIRM are my reading where the brief is silent.

## What this change is
Two public endpoints under `/api/v1/auth/`: `POST code/request/` (send a six-digit code by SMS)
and `POST code/verify/` (check it and sign the customer in with a session). It builds on the pure
rules in ADR 0010 (`otp.py`, `phone.py`) and the `SmsProvider` interface. No new app, no new
dependency. The migration for the two new tables is generated by the GitHub workflow
(`[gen-migrations]`, ADR 0011).

## Behaviour
- Request: always `202 {"expires_in_seconds": 300}` for a valid Ghana number, whether or not an
  account exists, so accounts cannot be probed. A staff or switched-off account gets the same
  answer and no code. A bad number is `400`.
- Verify: `200 {"is_new_customer", "user": {"id"}}` and a session. A wrong, expired, reused,
  missing or malformed code is `400` with `details.reason = "invalid_code"`. A locked code is `429`
  with `reason = "too_many_attempts"`.
- Other refusals: `429` with `retry_after_seconds` (too soon, too many codes, or too many requests
  from one address), `503` with `reason = "sms_unavailable"` (daily cap reached, no provider
  configured, or the provider refused the message), `403` with `reason = "bad_origin"`.
- Callers should read `details.reason`, not `error.code`: the code string for a status that
  already has one is chosen by `config/envelope.py`.

## Guarantees under simultaneous requests, and what enforces each
- **At most five wrong guesses per code.** The code's row is locked while it is checked, so
  simultaneous guesses are counted one at a time. Wrong guesses are saved even though the answer is
  an error (the outcome is returned from inside the transaction, never raised through it).
- **A code works once.** The same lock; consumed codes are ignored.
- **One code per number per minute, five per hour, one live code at a time.** Requests for one
  number take turns (a PostgreSQL advisory lock), with a partial unique constraint as the backstop.
  The concurrency test found a real flaw before this lock existed: of 25 simultaneous requests for
  one number, two were sent.
- **The daily SMS cap cannot be exceeded.** One `UPDATE ... WHERE count < cap` on a per-day row.
  A refused request does not use up the allowance. Default 500 a day for the whole site.
- **A customer account exists only after a correct code, and one number is one account.** The
  account is created in the same transaction that consumes the code, with the unique constraint on
  the normalised phone and a retry if two requests create it at once.
- **The session key is replaced at sign-in** (Django's `login()`), so a session id planted
  before sign-in is dead afterwards, and another user's session on the same browser is replaced.

## Where the limits live, and a conflict with ADR 0011 (CONFIRM)
The docstring in `otp.py` and ADR 0011 place the request-layer limits in the Redis cache. The
settings comment says that cache may evict keys. An evictable counter cannot be a hard cap, so:
- The limits that must never fail (wrong guesses, single use, per-number limits, the daily SMS cap)
  are in PostgreSQL.
- Only the per-address limits (30 code requests and 60 verify attempts an hour per address) stay in
  the cache, as a best-effort brake. Many Ghanaian phones share one carrier address, so these are
  deliberately generous. All limits can be overridden with a `LOGIN_CODE_LIMITS` setting.

## CSRF and cookies (review)
API views are exempt from Django's CSRF middleware, and these two views set a session cookie, so a
hostile web page could try to sign a visitor in as the attacker (login CSRF). `SameSite` helps but
is not relied on. Three layers (`origin.py`):
1. JSON only (a plain cross-site form cannot send it).
2. An `Origin` header, when present, must be this site or one of `CSRF_TRUSTED_ORIGINS`; `null` is
   refused.
3. With no `Origin`, a request the browser marks `Sec-Fetch-Site: cross-site` is refused.
Behind a proxy Django may see requests as plain http, so the storefront's own address must be in
`CSRF_TRUSTED_ORIGINS`.
**Not yet verified:** the production session-cookie settings. They must be: `SESSION_COOKIE_SECURE`
on, `SESSION_COOKIE_HTTPONLY` on, `SESSION_COOKIE_SAMESITE` `"Lax"` or stricter,
`SECURE_PROXY_SSL_HEADER` set correctly, and `CSRF_TRUSTED_ORIGINS` listing the storefront. This
needs a review of `config/settings/prod.py` and `staging.py`.

## Interpretations (CONFIRM)
1. A new number becomes a customer account on its first successful login.
2. Staff and switched-off accounts cannot use phone codes (staff use password and two-factor).
3. The fake SMS provider is used only with `SMS_PROVIDER="fake"` or when `DEBUG` is on. With
   nothing configured, staging and production refuse to send. **Never set `fake` in production.**
4. Requests without an `Origin` header (apps, curl) are allowed through.
5. A refused or lost message still counts against the daily cap, because the provider may have
   charged for it.

## How it was checked
Against PostgreSQL 16.15, with your `identity.User`, `otp.py`, `phone.py`, throttling and error
handler as pasted. 53 identity tests, 8 of them threaded concurrency tests (up to 40 simultaneous
requests); the concurrency tests were run 16 times with no failures. A mutation check broke the
code 26 ways (locks, caps, limits, staff rules, session rotation, origin rules, address limits,
provider selection, a database constraint, logging a code or a full number), and every one was
caught. Not yet run in your CI.

## Residual risks and not built yet
- An attacker can request codes for many numbers and use up the daily SMS cap, which blocks
  everyone's login for the rest of the day. The per-address limit slows this, not stops it.
  Alerting on the cap, and a real provider's own spend limit, are the next defences.
- Five guesses per code and five codes an hour allow about 25 guesses an hour against one number
  out of a million.
- Old `LoginCode` rows pile up; a cleanup task is not built.
- Logout, "who am I", Google sign-in, staff two-factor, the real SMS provider, and the
  production cookie review.
