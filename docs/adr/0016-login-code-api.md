# ADR 0016: Login by phone code, logout and "who am I"

Status: proposed. Items marked CONFIRM are my reading where the brief is silent.

## What this change is
Four endpoints under `/api/v1/auth/`: `POST code/request/` (send a six-digit code by SMS),
`POST code/verify/` (check it and sign the customer in with a session), `POST logout/` and
`GET me/`. It builds on the pure rules in ADR 0010 (`otp.py`, `phone.py`) and the `SmsProvider`
interface. No new app, no new dependency. The migration for the two new tables is generated by the
GitHub workflow (`[gen-migrations]`, ADR 0011).

## Behaviour
- Request: always `202 {"expires_in_seconds": 300}` for a valid Ghana number, whether or not an
  account exists, so accounts cannot be probed. A staff or switched-off account gets the same
  answer and no code. A bad number is `400`.
- Verify: `200 {"is_new_customer", "user": {"id"}}` and a session. A wrong, expired, reused,
  missing or malformed code is `400` with `details.reason = "invalid_code"`. A locked code is `429`
  with `reason = "too_many_attempts"`.
- Logout: `204`, also when nobody is signed in. The old session cookie stops working.
- Me: `200` with id, name, phone, email and `is_staff` for the signed-in user; `401` otherwise.
- Other refusals: `429` with `retry_after_seconds` (too soon, too many codes, or too many requests
  from one address), `503` with `reason = "sms_unavailable"` (allowance used up, no provider
  configured, or the provider refused the message), `403` with `reason = "bad_origin"`.
- Callers should read `details.reason`, not `error.code`: for a status that already has a code in
  `config/envelope.py`, that code is used instead of the one the view names.

## Guarantees under simultaneous requests, and what enforces each
- **At most five wrong guesses per code.** The code's row is locked while it is checked, so
  simultaneous guesses are counted one at a time. Wrong guesses are saved even though the answer is
  an error (the outcome is returned from inside the transaction, never raised through it).
- **A code works once.** The same lock; consumed codes are ignored.
- **One code per number per minute, five per hour, one live code at a time.** Requests for one
  number take turns (a PostgreSQL advisory lock), with a partial unique constraint as the backstop.
  The concurrency test found a real flaw before this lock existed: of 25 simultaneous requests for
  one number, two were sent.
- **The daily SMS allowance cannot be exceeded.** One `UPDATE ... WHERE count < ceiling ...
  RETURNING count` on a per-day row. A refused request does not use up the allowance. Default 500
  a day for the whole site.
- **Existing customers keep part of the allowance.** Of the 500, 100 are reserved for numbers that
  already have an account. Numbers with no account can use only the other 400. A flood of requests
  for made-up numbers therefore cannot stop real customers logging in.
- **A customer account exists only after a correct code, and one number is one account.** The
  account is created in the same transaction that consumes the code, with the unique constraint on
  the normalised phone and a retry if two requests create it at once.
- **The session key is replaced at sign-in** (Django's `login()`), so a session id planted
  before sign-in is dead afterwards, and another user's session on the same browser is replaced.

## Alerts
The database count is the only source, so each alert fires exactly once, even when requests race:
a warning when new numbers, or customers, pass 80% of their allowance, and an error (which goes to
Sentry) when each allowance is used up. Messages contain no phone numbers. The SMS provider's own
spend limit, set in the provider's dashboard when it is chosen, is the second line of defence.

## Housekeeping
`purge_old_login_codes()` deletes login codes older than seven days, in batches of 1,000, and
`identity.tasks.purge_old_login_codes` runs it. It must be added to the Celery beat schedule, once a
day. The daily SMS counts are kept (one small row a day, useful for cost).

## Where the limits live, and a conflict with ADR 0011 (CONFIRM)
The docstring in `otp.py` and ADR 0011 place the request-layer limits in the Redis cache. The
settings comment says that cache may evict keys. An evictable counter cannot be a hard cap, so:
- The limits that must never fail (wrong guesses, single use, per-number limits, the SMS allowance)
  are in PostgreSQL.
- Only the per-address limits (30 code requests and 60 verify attempts an hour per address) stay in
  the cache, as a best-effort brake. Many Ghanaian phones share one carrier address, so these are
  deliberately generous. All limits can be overridden with a `LOGIN_CODE_LIMITS` setting.

## CSRF and cookies (review)
API views are exempt from Django's CSRF middleware, and the login views set a session cookie, so a
hostile web page could try to sign a visitor in as the attacker (login CSRF). `SameSite` helps but
is not relied on. Three layers (`origin.py`), applied to code request, verify and logout:
1. JSON only (a plain cross-site form cannot send it).
2. An `Origin` header, when present, must be this site or one of `CSRF_TRUSTED_ORIGINS`; `null` is
   refused.
3. With no `Origin`, a request the browser marks `Sec-Fetch-Site: cross-site` is refused.

Review of `prod.py` and `staging.py`: they already had `SESSION_COOKIE_SECURE`,
`CSRF_COOKIE_SECURE` and the proxy header. Added and now tested (`test_deployed_settings.py`):
- `SESSION_COOKIE_HTTPONLY` and `SameSite=Lax` for the session and CSRF cookies, written out rather
  than left to Django's defaults.
- `CSRF_TRUSTED_ORIGINS` read from an environment variable of the same name (comma separated),
  keeping anything `base.py` lists. **It must be set in staging and production to the storefront's
  address (for example `https://www.example.com`).** If the storefront is on a different origin
  from the API and is not listed, the Origin check refuses its logins.
- The storefront and the API should share one registrable domain (for example `www.` and `api.`),
  so `SameSite=Lax` cookies work. A different domain would need `SameSite=None`, which weakens the
  second layer; do not do that without a new decision.

Not changed, CONFIRM: `SECURE_HSTS_SECONDS` and `SECURE_SSL_REDIRECT` (Cloudflare may already do
both; turning HSTS on is hard to undo), the `__Host-` cookie name prefix, and the session lifetime
(Django's default is two weeks).

Logout is protected by the Origin check rather than a CSRF token, so the storefront needs no token
for it. The worst a forged logout could do is sign a visitor out. The other authenticated API views
keep Django's CSRF token check.

## Interpretations (CONFIRM)
1. A new number becomes a customer account on its first successful login.
2. Staff and switched-off accounts cannot use phone codes (staff use password and two-factor).
3. The fake SMS provider is used only with `SMS_PROVIDER="fake"` or when `DEBUG` is on, and it is
   refused outright when `DJANGO_SETTINGS_MODULE` ends in `.prod` or `.staging`. With nothing
   configured, those environments refuse to send.
4. Requests without an `Origin` header (apps, curl) are allowed through.
5. A refused or lost message still counts against the allowance, because the provider may have
   charged for it.
6. 100 of the 500 daily messages are reserved for existing customers.
7. `me` returns the user's own phone and email in full, to that user only, and is never cached.

## How it was checked
Against PostgreSQL 16.15, with your `identity.User`, `otp.py`, `phone.py`, throttling and error
handler as pasted. 89 identity tests, 10 of them threaded concurrency tests (up to 40 simultaneous
requests); the concurrency tests were run 28 times in all with no failures. A mutation check broke
the code 45 ways (locks, caps, limits, the customer reserve, alerts, staff rules, session rotation,
origin rules, address limits, provider selection, a database constraint, cleanup, logout, `me`, the
cookie settings, logging a code or a number), and every one was caught. Not yet run in your CI.

## Residual risks and not built yet
- An attacker who knows real customers' numbers can still use the reserved 100 messages, five per
  number per hour. Real customers get an SMS they did not ask for. A challenge step (for example
  Cloudflare Turnstile) on code requests is the proper next defence; it needs an HTTP client, so it
  needs a dependency proposal.
- Five guesses per code and five codes an hour allow about 25 guesses an hour against one number
  out of a million.
- The cleanup task is not on the beat schedule yet (one line in `base.py`).
- Google sign-in (`django-allauth` is in the stack, but it needs Google credentials from the
  client, and it is item 3 on the cut line), staff TOTP two-factor (a library needs approval), the
  real SMS provider, and password login for staff.
