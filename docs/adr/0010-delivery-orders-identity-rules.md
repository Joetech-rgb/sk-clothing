# ADR 0010: Delivery, order-state, login-code and phone rules (pure core)

Status: proposed. Everything marked CONFIRM is my reading of the brief where it is silent.

## What this change is
The business-rule core for the rest of Phase 1A, as pure Python (no database, no clock), tested
without Django: delivery fees and quotes, the delivery code, Ghana phone numbers, login codes, the
order state machine, pickup timing, and the interfaces for SMS, email and search. The Django
layers (models, endpoints, admin, tasks) are built on top of these next.

## Taken directly from the brief
- Doorstep fee = max(minimum, base + rate x km). km = straight-line distance times a road factor
  (1.3). Beyond the maximum distance: awaiting quote. All values are settings. Unlisted station:
  awaiting quote. Pickup is free. Pay on delivery only for Accra doorstep.
- Delivery code: six digits, stored as an HMAC, five attempts then lockout.
- Login code: six digits, stored hashed, five-minute expiry.
- Pickup: held 7 days, reminder on day 3, uncollected after day 7.
- Payment, fulfilment and refund are three separate fields, with an explicit transition table.

## Interpretations (CONFIRM)
1. **"Accra doorstep" means a doorstep order that could be priced**, i.e. inside the maximum
   distance. The brief gives no other definition of Accra. Pay on delivery is allowed exactly then.
2. **The maximum distance is compared with the road-adjusted km**, the same km the fee uses.
3. **The fee is rounded half up to a whole pesewa.** The brief gives no rounding rule. If the shop
   prefers whole cedis, it is a one-line change.
4. **Station names match ignoring case and spacing**, nothing fuzzier.
5. **Wrong-guess limit on login codes: five per code.** The brief throttles requests but gives no
   limit on guesses; without one, six digits in five minutes can be brute-forced. A malformed entry
   (not six digits) does not count as a guess, for both login and delivery codes.
6. **Phone numbers are Ghana only** (+233, nine digits, not starting with 0), stored as E.164.
   Foreign numbers are refused. Whether a number is a mobile (the 02x and 05x ranges) is not
   checked, because I have not verified the national numbering plan.
7. **An order out for delivery cannot be cancelled.** The brief has no failed-delivery flow, so
   cancelling then would leave goods with a rider. Needs a rule before it is allowed.
8. **Pay on delivery cash is treated as paid when the rider enters the delivery code.**

## Order state tables (proposed, CONFIRM)
Payment: pending, paid, failed (may be retried), cod_pending, cod_confirmed, void (cancelled
before any money was taken). Fulfilment: awaiting_quote, pending, to_pack, packed,
ready_for_pickup, out_for_delivery, delivered, collected, uncollected, cancelled, not_fulfillable.
Refund: none, requested, submitted, processing, processed, failed, manual_resolution.
Whether an order is a pickup order is fixed when it is created and never changes.

| Event | Effect |
|---|---|
| quote_set | awaiting_quote to pending |
| payment_confirmed | pending, failed or void payment becomes paid; pending fulfilment becomes to_pack; if the order is already cancelled or not_fulfillable, a refund is requested |
| payment_failed | pending payment becomes failed (not before the fee is set) |
| cod_confirmed | cod_pending becomes cod_confirmed; pending becomes to_pack |
| stock_unavailable | pending or to_pack becomes not_fulfillable; a paid order gets a refund requested, an unpaid one is voided |
| packed | to_pack to packed |
| ready_for_pickup, collected, flag_uncollected | pickup orders only, from packed, then ready, then collected or uncollected |
| dispatched, delivered | delivery orders only; delivered also marks pay-on-delivery cash as paid |
| cancel | from awaiting_quote through uncollected (not out_for_delivery); a paid order gets a refund requested, an unpaid one is voided |
| refund_submitted, refund_processing, refund_processed, refund_failed | the refund path |
| refund_retry, refund_escalated, refund_resolved_manually | a failed refund is retried, or escalated to a person, who can mark it done |

Repeating an event that already happened is a harmless no-op, so replayed webhooks and
double-clicks cannot do damage.

## How it was checked
The state machine is searched exhaustively: every state any order can reach (46 of them) is
generated by trying every event from every state, and each is checked against rules such as "an
order is never handed over unpaid", "a paid dead order always has a refund path", "a finished order
never moves again", and "a refund is never started twice". The check found two real flaws while it
was being written (an unpayable order that could be marked payment-failed, and the machine not
knowing pickup from delivery), and a mutation test found a third (a refund that could restart
after it had finished). All three are fixed and have tests.

## Not built yet
The database models and endpoints for all of this, the Redis rate limits (per number, per IP, the
daily SMS spend cap), real SMS and email providers, and the Postgres search implementation.
